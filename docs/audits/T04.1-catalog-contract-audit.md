## 1. Executive Summary

1. **Code fact:** the merged T04.0-R baseline is not Site-centric. It has no
   `SiteId`, `SourceId`, `FirstBatchSourceId`, Site DTO, Site repository, Site
   search contract, or `/sites` route. Its active boundary is the transitional
   `ArchiveItem*` contract, `ArchiveCatalogReader`, and `GET /v1/items` plus
   `GET /v1/items/{id}`.
2. **Code fact:** the active `ArchiveItemId` denotes an opaque platform digital
   archive item, not a physical Site and not a source record. The ID is
   therefore currently a platform content-entry identity (Identity Q1: B for the
   active ID), although the surrounding DTO remains deliberately
   inscription-first.
3. **Historical evidence:** the last `SiteId` definition described itself as a
   generic platform entity identity, while its DTOs, methods, and routes also
   used physical-site concepts such as region, coordinates, address, and related
   sites. The historical Site model therefore mixed platform-entry and
   physical-site semantics (C). This finding does not make `SiteId` a current
   symbol.
4. **Code fact:** the current Public DTO surface is intentionally narrow and
   uses strict Zod objects. It excludes raw source, review/evidence, lifecycle,
   persistence, media, object keys, detailed region, and relationships. The main
   remaining architectural gap is that the transitional read port returns Public
   DTOs directly, leaving no internal Catalog record/read projection or explicit
   mapper boundary.
5. **Recommendation:** introduce `Catalog` as the domain term, `CatalogId` as
   its canonical platform identity, and a three-value `CatalogKind`. Keep the
   common shell small; do not force place-, object-, or calligraphy-specific
   facts into it. Keep `SourceId` distinct and reserve any future `SiteId`
   exclusively for a physical place/heritage-site domain.
6. **Recommendation:** use an application-owned query abstraction that returns
   internal list/detail projections, followed by an explicit API mapper to
   Public DTOs. Of the names audited, `CatalogQueryPort` best matches the
   repository's accepted “Query Port” vocabulary and avoids traditional
   aggregate-repository implications. The name remains a recommendation, not a
   frozen Owner decision.
7. **Code fact:** no repository-internal runtime consumer of `/v1/items` exists.
   There is no HTTP server/router/handler or read-port implementation, and the
   frontend/runtime workspaces do not consume the route or Archive contracts.
   This supports D6-FINAL's future controlled migration to `/v1/catalog` without
   permanent dual routes. **Inference:** repository-external consumers cannot be
   disproved from source code and require a migration preflight.
8. No production code, frontend, tests, OpenAPI, database, or runtime
   implementation needs to change during T04.1-A.

### 4.3 Semantic classification

1. **Genuine place/heritage-site semantics:** region, coordinates, address,
   `relatedSites`, site code, and the term “inscription site.”
2. **Generic platform content semantics:** opaque platform identity, title,
   aliases, period, categories, description, images, references, and
   search/list/detail.
3. **Generic behavior carrying a Site name:** the historical `CatalogRepository`
   operated on Sites as the only platform entry type, even though many
   operations were generic catalog reads.

**Conclusion:** there is no current Site model to classify. The historical Site
model was mixed (C): its ID comment and repository role treated Site as the
generic platform entity, while its DTO and API language also modeled a physical
or heritage site. The assumption “platform content = Site” existed historically
in the public DTO, method names, routes, and repository surface; it was removed
from the merged T04.0-R boundary rather than generalized in place.

## 5. Catalog Generalization Gaps

### 5.1 Problems Catalog must solve

**Code fact:** the active boundary calls the entity `ArchiveItem`, but ADR 0003
says that name and `/v1/items` are transitional and that T04.1 will freeze
Catalog language
(`docs/adr/0003-inscription-first-public-archive-boundary.md:17-33`).

The current model cannot express:

- which of the three approved content kinds an item represents;
- a stable internal Catalog record distinct from its public response;
- subtype-specific facts without adding them to every item;
- an application-owned read projection and explicit Public DTO mapper;
- the canonical Catalog identity and route vocabulary.

Current `provinceLabel` and `protectionOrCollectionUnitLabel` are safe display
values, but they are inscription-first. A calligraphy work may have a holding
collection rather than a protected physical site; a cliff inscription may
require site context that a calligraphy work cannot have. Retaining these as
universal required domain concepts would reproduce the earlier semantic
conflation.

### 5.2 Recommended common shell

**Recommendation:** the minimum common Catalog shell should cover only facts
shared by all three kinds:

- canonical `CatalogId`;
- `CatalogKind`;
- canonical display title and aliases;
- optional public-facing summary and description;
- optional historical-period attribution suitable for display;
- an internal provenance association boundary, mapped separately to curated
  public citations when appropriate.

Media references may eventually be common but remain T05-owned. Lifecycle,
publication, audit, timestamps, and persistence fields are internal concerns and
should not be added merely to make the first shell appear complete.

### 5.3 Facts not to force into the common shell

- **Inscription:** carrier/material, physical dimensions, inscription text or
  word count, engraver/inscriber roles, preservation, and holding/protection
  facts.
- **Cliff inscription:** physical Site/location, cliff surface and orientation,
  carving context, coordinates, and site protection facts.
- **Calligraphy:** album/scroll/leaf format, paper/silk/material, edition or
  impression/folio facts, collection history, and calligrapher attribution.

These are domain categories for later subtype design, not proposed T04.1
schemas. T04.1 should provide an extension boundary without inventing fields for
seal, painting, sculpture, video, or user-generated content.

### 6.2 Q1 — What does current SiteId mean?

**Code fact:** no `SiteId` exists in the current merged baseline, so A/B/C is
not applicable to a current symbol.

For the last historical implementation, the narrow ID definition itself says B
(platform entity identity), but the consuming public model and route combine A
and B. Therefore the historically implemented Site boundary as a whole is C
(mixed semantics). This distinction prevents a historical type comment from
being mistaken for proof of a clean physical Site aggregate.

For the active identity, `ArchiveItemId` is B:

- OpenAPI calls it an “Opaque platform ArchiveItemId”
  (`services/public-api/src/openapi-document.ts:97-103`).
- ADR 0003 defines `ArchiveItem` as a platform-managed and publicly displayed
  digital archive entry, and explicitly says it is not a SourceRecord, media
  key, community post, or product
  (`docs/adr/0003-inscription-first-public-archive-boundary.md:17-27`).
- Contract tests accept an arbitrary platform format and reject source-like
  whitespace patterns
  (`tests/unit/contracts/archive-item-contracts.test.ts:110-117`).

### 6.3 Q2/Q3 — Need for CatalogId and its safe relationships

**Recommendation:** yes, `CatalogId` is theoretically and, under D5, canonically
needed. The safe long-term invariants are:

```text
CatalogId != SourceId
CatalogId != future physical SiteId
ArchiveItemId = transitional compatibility name for the same platform-content identity
```

The last line describes logical identity, not an instruction to globally rename
the current code. A future migration can initially make `ArchiveItemId` a
deprecated type/schema alias of the canonical Catalog identity while preserving
opaque wire values. It must never alias `SourceId`.

### 6.4 Q4 — Catalog, Site, and Source relationships

**Recommendation:** the future conceptual model should use independent
associations:

```text
CatalogRecord ── 0..n ──> future Site/location domain
CatalogRecord ── 1..n ──> SourceRecord/provenance
```

**Inference:** exact source and Site cardinalities require validated data and
are not proven by the current repository. Sources must attach to Catalog
independently of a Site because calligraphy may have no physical heritage site
and provenance describes the cataloged work, not merely its location. D8
therefore correctly defers Site contracts and all cardinality implementation.

### 6.5 Q5 — Identity migration blast radius

| Area                | Current impact of adopting canonical `CatalogId`                                | Compatibility note                                                                          |
| ------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Zod/type source     | `archiveItemIdSchema`, `ArchiveItemId`, summary/detail IDs                      | New Catalog symbols can be additive before old names are removed                            |
| JSON Schema/OpenAPI | `ArchiveItemId` component and detail path parameter                             | Renaming/removing components is breaking to generated clients                               |
| Public DTO names    | all `ArchiveItem*` exports and strict schemas                                   | Required `kind` cannot be added to existing DTO without a response-shape break              |
| Query/page names    | `ArchiveItemList*`, `ArchiveItemPage`                                           | New Catalog names may coexist only during a bounded migration                               |
| Read port           | imports, `getItemById`, return types, adapter contract suite                    | Port move/name/output changes are source breaking for implementations; none currently exist |
| API                 | `/v1/items`, `{id}`, operation IDs, descriptions, possible error code naming    | Route and operation rename is contract breaking, but no in-repo runtime consumer exists     |
| Tests               | contracts, reader suite, OpenAPI, contracts surface, frontend allowed-type list | Many tests intentionally freeze exact current names/surfaces                                |
| Docs/ADR            | contracts/data-access/public-api READMEs, architecture, status, ADR 0003        | Must distinguish superseded transitional decisions from retained principles                 |
| Frontend            | no current import or route use                                                  | No current `apps/web` change is needed                                                      |

Historical Site files are not part of the current migration blast radius because
they are absent from merged integration. They must not be resurrected merely to
rename them.

### 6.6 Recommended identity migration sequence

1. Add canonical `CatalogId` and Catalog DTO/read-model symbols without deleting
   `ArchiveItemId` in the same step.
2. Establish that compatibility names carry the same opaque platform identity;
   add tests that continue to reject `SourceId` substitution.
3. Migrate the application-owned query port and mapper to Catalog identity.
4. In the separate route migration task, change path/components/operation IDs to
   Catalog vocabulary after repeating consumer discovery.
5. Remove Archive compatibility exports only in an explicitly scoped cleanup
   after all consumers and generated artifacts have migrated.

## 7. CatalogKind Analysis

**Recommendation:** establish `CatalogKind` with a Zod enum as the runtime
source:

```ts
const catalogKindSchema = z.enum([
  "inscription",
  "cliff_inscription",
  "calligraphy",
]);
type CatalogKind = z.infer<typeof catalogKindSchema>;
```

Reasons:

- the repository already uses Zod as the runtime source of truth;
- an inferred literal union provides exhaustive TypeScript typing without
  emitting a TypeScript enum runtime object;
- one ordered schema source feeds JSON Schema/OpenAPI;
- adding a future approved literal does not require redesigning the
  representation.

Adding enum members is additive for the service but can affect clients with
exhaustive switches; future clients should have an unknown/fallback presentation
policy. T04.1 must not add placeholder literals or subtype schemas for unfrozen
content kinds.

## 8. Internal Record vs Public DTO Boundary

### 8.1 Current state

**Code fact:** no internal record currently exists. `ArchiveCatalogReader`
directly returns `ArchiveItemSummary`, `ArchiveItemDetail`, and
`ArchiveItemPage` Public DTOs. This is safe against field leakage today because
the DTOs are strict and small, but it couples the read abstraction to the
HTTP-facing shape.

Contract tests explicitly reject lifecycle, raw source, import, review,
evidence, database/ORM, media/storage, relations, detailed region, and category
fields (`tests/unit/contracts/archive-item-contracts.test.ts:57-91`). OpenAPI
tests also assert that internal terms are absent
(`tests/unit/backend/openapi-contract.test.ts:82-109`).

### 8.2 Recommended layers

1. **Internal domain record — `CatalogRecord`**
   - application/domain-owned;
   - carries canonical identity/kind/common facts and internal provenance links;
   - not exported from the public contracts root and never serialized directly.
2. **Internal read projections**
   - purpose-specific list and detail read shapes returned by the query port;
   - may contain internal identifiers or already-resolved facts needed by the
     mapper;
   - must not contain raw-source blobs or infrastructure handles simply because
     they are internal.
3. **Public DTOs — recommended names `CatalogSummaryDto`, `CatalogDetailDto`,
   and `CatalogSummaryPageDto`**
   - defined and validated at `@moya/contracts`;
   - strict, display-oriented, and transport-safe;
   - produced only through an explicit mapper/API boundary.
4. **Transport query**
   - keep HTTP query strings separate from normalized application list input;
   - use `CatalogListTransportQuery` and `CatalogListQuery` rather than a
     generic `CatalogQuery` that could silently grow search/feed semantics.

Search result/highlight/relevance projections are T08 responsibilities. A list
summary may be reusable input to future T08 design, but T04.1 must not freeze
`CatalogSearchItemDto` or `CatalogSearchPageDto`.

### 8.3 Allowed public concepts

- `CatalogId` and `CatalogKind`;
- display title, aliases, summary, and description;
- approved display-only historical period;
- approved display-only location, protection, or holding labels when
  semantically appropriate and optional;
- curated public citation label/text/public URL;
- stable pagination metadata;
- future backend-resolved media URL, alt text, and caption only when T05 defines
  the media boundary.

### 8.4 Internal-only concepts

- `SourceId`, `FirstBatchSourceId`, raw SourceRecord and source-specific
  metadata;
- raw region strings, candidate regions, evidence, verification state,
  selection, human decisions, review notes, and D01 governance data;
- ingestion batch/path/hash and source file implementation metadata;
- internal lifecycle, moderation, deletion, publication workflow, admin notes,
  and audit metadata;
- database/ORM IDs and persistence metadata not designated as public identity;
- object keys, bucket/provider configuration, credentials, and storage resolver
  internals;
- internal Site association and physical-location evidence until a separate
  domain contract approves their public projection.

`PublicSourceCitation` is currently safe because it contains curated public
fields, not SourceRecord identity or raw metadata. Its `sources` container name
may be misread as raw provenance; the Catalog DTO design should consider the
more explicit `sourceCitations` or `citations`, without changing the current
contract during this audit.

## 9. Repository Port Analysis

### 9.1 Current and historical coupling

**Code fact:** the current `ArchiveCatalogReader` is no longer Site-bound and
has only list/get operations. It is still coupled to Archive naming and Public
DTO outputs.

**Historical evidence:** the old `CatalogRepository` was Site-bound and
contained `listSites`, `getSiteById`, `searchSites`, region facets, and category
facets. It was also called a “stable catalog persistence port” while returning
Public DTOs. That surface mixed persistence, public projection, search,
taxonomy, and Site terminology and should not be restored.

### 9.2 Naming comparison

| Candidate               | Strength                                                                                           | Risk                                                                                                                | Assessment                                               |
| ----------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `CatalogReadRepository` | familiar read-side repository name                                                                 | “Repository” suggests persistence/aggregate loading, which current ADR explicitly distinguishes from the Query Port | acceptable only with strong documentation, not preferred |
| `CatalogQueryPort`      | matches Accepted ADR and README vocabulary; emphasizes application boundary and normalized queries | could later attract unrelated query methods without ownership discipline                                            | recommended                                              |
| `CatalogReadPort`       | neutral and clearly read-only                                                                      | less aligned with current repository vocabulary; vague about projection/query role                                  | viable second choice                                     |
| `ArchiveCatalogReader`  | already implemented and read-only                                                                  | transitional Archive name, package location, and direct Public DTO returns                                          | retain only until migration                              |

**Recommendation:** `CatalogQueryPort`, application-owned within the future
Catalog application module. This is a naming recommendation, not a frozen
contract.

Its T04.1 capability should be limited to normalized list and get-by-CatalogId.
It must return internal list/detail projections, not Public DTOs. The
application/API mapper produces `CatalogSummaryDto`/`CatalogDetailDto`. Do not
add create/update, publication, card, homepage, feed, recommendation, facet, or
search methods.

The port must not be frontend-owned or exported as a browser dependency. UI card
shapes are presentation concerns; future feed and search consumers should define
their own application projections rather than mutate the base Catalog query
port.

## 10. Public API / OpenAPI Analysis

### 10.1 Current API facts

- OpenAPI version: 3.1.1, JSON Schema dialect Draft 2020-12
  (`services/public-api/src/openapi-document.ts:50-57`).
- Paths: `/health`, `/v1/items`, `/v1/items/{id}` only.
- List parameters: `page`, `pageSize`; no filters or sorting.
- Detail parameter: opaque `ArchiveItemId` component.
- Responses: list 200/400/500/503; detail 200/404/500/503; health 200/503.
- Error model: stable envelope with code/message/requestId.
- No search, categories, regions, feed, or mutation route.

### 10.2 Source-of-truth chain

**Code fact:** the chain is:

```text
Zod schema
→ z.infer TypeScript type
→ z.toJSONSchema(..., draft-2020-12)
→ manually composed OpenAPI 3.1.1 path/component document
→ deterministic serialized openapi.json
```

The component data schemas come from `@moya/contracts/json-schema`; paths, HTTP
placement, operations, statuses, and descriptions are authored by
`services/public-api/src/openapi-document.ts`. The generator builds the package,
serializes the document, and formats the artifact
(`services/public-api/scripts/generate-openapi.mjs`). The OpenAPI test compares
the regenerated object with the committed artifact
(`tests/unit/backend/openapi-contract.test.ts:122-134`).

### 10.3 Canonical Catalog route

D6-FINAL establishes future `GET /v1/catalog` and `GET /v1/catalog/{catalogId}`.
The current `/v1/items` routes must remain unchanged in T04.1-A. A later
controlled migration must update paths, parameters, component names, operation
IDs, response schemas, tests, generated JSON, and documentation as one contract
change.

The historical `/v1/sites` routes do not exist in merged integration, so there
is no current `/sites` compatibility surface to retain or delete.

### 10.4 Consumer audit

Repository searches covered apps, packages, services, manifests, imports,
routes, tests, and all available local refs.

**Code facts:**

- `apps/web`, `apps/admin`, and `packages/ui` do not import Archive contracts,
  `@moya/data-access`, or `@moya/public-api` and do not reference `/v1/items`.
- The web and admin manifests depend only on Next/React runtime packages, not
  Moya data/runtime packages (`apps/web/package.json`,
  `apps/admin/package.json`).
- `packages/search` and `packages/image` do not consume the route or contracts.
- `services/public-api` has no server, router, or handler.
- `ArchiveCatalogReader` has no production implementation.
- `/v1/items` occurrences are limited to contract/OpenAPI source and artifact,
  contract/architecture tests, and documentation.

**Conclusion:** there is no repository-internal runtime consumer and no current
compatibility requirement supported by code. This evidence supports D6-FINAL's
default controlled single-route migration rather than indefinite aliases.

**Inference / externally unverified:** source code cannot prove that nobody has
copied or generated a client from the committed OpenAPI artifact. Before the
actual route migration, confirm release/deployment status and known external
consumers. If a real consumer is found, use a finite, explicitly sunset
compatibility window.

## 11. Compatibility / Breaking-change Analysis

### 11.1 Additive or compatibility-preserving changes

- add `CatalogKind`, `CatalogId`, new Catalog DTO/schema/type exports while
  retaining transitional Archive exports;
- add internal Catalog record/read projection and mapper without changing
  current responses;
- add an application-owned query port while existing `ArchiveCatalogReader`
  remains temporarily available;
- add architecture guards for the future Catalog module and public Catalog DTO
  type-only imports;
- document deprecations and migration sequencing.

These changes are additive only if required fields are not injected into
existing strict Archive response schemas and existing exported types are not
silently redefined incompatibly.

### 11.2 Breaking changes

- replacing `ArchiveItemId` exports with `CatalogId` without an alias period;
- adding required `kind` to existing `ArchiveItemSummary`/`Detail`;
- renaming/removing Archive DTO, page, or query exports;
- moving/removing `ArchiveCatalogReader` or changing its method
  signatures/outputs;
- changing `/v1/items` to `/v1/catalog`, path parameter/component names,
  operation IDs, or response schemas;
- changing `ITEM_NOT_FOUND` if clients bind to error-code enums;
- removing or changing OpenAPI components used by generated clients;
- changing pagination wire shape or defaults.

### 11.3 Recommended compatibility policy

Use additive internal/model preparation first, followed by one explicit
controlled contract migration. Do not keep two equivalent routes indefinitely.
Because there is no runtime implementation or known in-repo consumer, a later
single migration is lower risk than permanent alias infrastructure. Archive
compatibility types can outlive the route briefly if source-level consumers need
sequencing, but their removal must be a separately visible change.

Do not reintroduce historical `/sites`, Site DTOs, or T01/D01 models as
compatibility aliases; they are not part of the merged baseline.

### 12.2 Guard gaps relevant to T04.1

- The Client Component approved-type allowlist is hard-coded to Archive DTO

  with Catalog Public DTOs.
- Type-only enforcement and the public-type allowlist are applied specifically
  to files with `"use client"`; all frontend source should retain the documented
  rule that contracts are type-only, including future server-rendered
  presentation code.
- Direct raw dataset access is well guarded, but a scanner cannot prove that an
  arbitrary HTTP payload does not contain `rawSource` or evidence. Strict Public
  DTO and OpenAPI negative-field tests remain essential.
- Object-key URL composition is detected, but merely carrying a locally defined
  `objectKey` field is not universally rejected. Future media contracts should
  make storage details structurally impossible at the Public DTO boundary and
  add targeted architecture tests rather than rely only on token scanning.

### 12.3 Recommended T04.1 guard updates

In the later implementation task, not this audit:

- replace/add the approved public type allowlist for Catalog DTOs and IDs;
- forbid imports from the future Catalog application/runtime module in every
  frontend workspace;
- require type-only public contract imports consistently across frontend source;
- retain negative schema/OpenAPI assertions for raw source, SourceId, review,
  evidence, object keys, storage, and admin fields;
- keep `packages/ui` domain-agnostic.

No `apps/web` modification is needed to accomplish the Catalog contract work.

## 13. Recommended T04.1 Target Architecture

```text
SourceRecord / provenance (internal, independent of Site)
             │
             ▼
       CatalogRecord
       - CatalogId
       - CatalogKind
       - minimal common facts
             │
             ├── future optional Site/location association (not T04.1)
             │
             ▼
  internal list/detail read projections
             │
             ▼
     application-owned CatalogQueryPort
             │
             ▼
      explicit API/DTO mapper
             │
             ▼
 CatalogSummaryDto / CatalogDetailDto / page
             │
             ▼
        OpenAPI / HTTP
             │
             ▼
          Frontend
```

Key invariants:

- Catalog identity, Source identity, and future physical Site identity remain
  distinct.
- Internal record and read projections are not public contract exports.
- Query port returns internal projections, never Public DTOs.
- Mapper owns visibility and semantic conversion.
- List/detail are the only T04.1 read capabilities.
- Search, Home Feed, card, recommendation, media, database, and Site contracts
  stay outside the task.
- Public routes ultimately use `/v1/catalog` and `/v1/catalog/{catalogId}`, but
  only a later controlled migration changes the existing contract.

## 14. Proposed Implementation Sequence

This sequence is for later Owner-authorized tasks; none is executed by T04.1-A.

1. **Design freeze:** record the Catalog common shell, kind, identity
   separation, internal/public layer boundaries, query-port naming decision, and
   compatibility plan in an ADR or technical contract.
2. **Additive contract preparation:** add Catalog ID/kind and new Public DTO
   schemas, inferred types, JSON Schemas, and negative-field tests while
   retaining Archive compatibility names.
3. **Internal/application boundary:** add the internal Catalog record and
   list/detail projections, application-owned query port, and explicit mapper
   contract tests.
4. **Architecture governance:** update dependency/allowlist guards for Catalog
   Public types and block frontend access to the new application/runtime module.
5. **Controlled API migration:** repeat consumer discovery, then migrate OpenAPI
   from `/v1/items` to `/v1/catalog` with all components, operation IDs, tests,
   generated artifacts, and docs in one scoped task. Add a time-bounded
   compatibility route only if a real external consumer is identified.
6. **Transitional cleanup:** remove Archive compatibility exports and the
   `packages/data-access` transitional port only after all known consumers
   migrate.
7. **Deferred tasks:** T05 media, T08 search, and any future Site/location
   domain proceed independently and consume Catalog identity through explicit
   contracts.
