## 1. 目标与边界

本规范冻结长期Catalog bulk input的canonical representation、Owner
workbook、CSV、dry-run与Import Batch contract。PostgreSQL仍是production runtime
source of truth；XLSX是Owner/Editor working format；CSV/canonical rows是bulk
interchange boundary。

历史T05.4-A/A.1
checkpoint只实现schema、specification、测试和无真实数据的安全空白template；当时不包含XLSX
parser、diff、apply或database migration。后续批准的persistence
pipeline已经实现strict CSV parser、PostgreSQL-backed dry-run、hash-bound
approval、transactional apply与durable operation audit。当前T05.4-B实现bounded
XLSX parser；Admin、publication、Media、UGC、Evidence
Domain和真实数据导入仍未实现。

```text
CSV bundle / XLSX workbook
→ version check
→ parsed table rows
→ canonical rows + shared validation
→ identity conflict / duplicate analysis
→ diff + capability blockers
→ dry-run
→ approval bound to canonical hashes
→ transactional apply
→ PostgreSQL
```

- 当前`catalog_entries`可承载CatalogId、kind、title、事实字段value/state、description
  value/state以及既有read-model字段；`catalog_aliases`可保存alias与required
  `alias_type`。
- `catalog_import_sources`保存SourceId linkage与raw provenance metadata；

- Public DTO/OpenAPI已严格拒绝SourceId、raw
  source、owner/review、storage与migration字段。
- T05.4-A历史checkpoint的raw dataset importer
  allowlist为空；T05.4-B当前实现仅授权同时具有allowlist与`controlled-importer`

## 3. Versioned canonical import model

Internal contract只从`@moya/contracts/internal/catalog-import`导出。Public
root、OpenAPI和Frontend不能导入该subpath。

### 3.1 Contract version

v1唯一合法值为`catalog-import/v1`。Canonical
envelope、dry-run、approval与batch都必须显式携带该值；missing/unknown
version在row validation之前失败。Workbook在
`99_Instructions`保存machine-readable metadata；CSV bundle必须包含单行
`00_manifest.csv`。不得从文件名或sheet布局猜测version。

### 3.2 Identity

```text
CatalogImportId != SourceId
CatalogImportId != CatalogId
SourceId != CatalogId
CatalogId != future SiteId
```

- `catalogImportId`：同一workbook/batch内的临时关联键；不持久化，不是第四套domain
  ID。
- `sourceId`：source-record identity。`01_Catalog`中的值是primary source
  identity。
- `catalogId`：optional；blank表示create candidate，VALUE表示update target。
- `catalogId`和已经建立的SourceId→CatalogId linkage不能通过普通import改写。

### 3.3 Canonical rows

`CanonicalCatalogImportEnvelope`包含`catalogRows`、`aliasRows`与
`provenanceRows`。v1没有position/order字段，因此三组row
collection的提交顺序只属于XLSX/CSV presentation，不属于domain
semantics；单纯重新排列worksheet或CSV rows不得改变`canonicalInputSha256`。

Hash representation的算法冻结为：

1. 先验证明确的`importContractVersion`，再完整验证canonical envelope、row
   contents与跨row uniqueness/reference invariants；无效输入没有canonical hash。
2. 不修改validated input，复制三组数组并分别升序排序：
   - `catalogRows`：tuple `[catalogImportId]`
   - `aliasRows`：tuple `[catalogImportId, alias]`
   - `provenanceRows`：tuple `[catalogImportId, sourceId]`
3. Tuple逐项比较；每项采用ECMAScript String relational
   comparison的locale-independent UTF-16 code-unit lexicographic
   order。不使用`localeCompare`，不做Unicode normalization、case
   folding、trim或其他值转换。现有uniqueness规则保证每个sort
   key在所属collection内唯一。Canonical hash输入的所有string必须是well-formed
   UTF-16；unpaired surrogate失败而不是被替换。
4. 保留row内全部validated values、tagged field
   states与`importContractVersion`，然后按RFC 8785-compatible object-key
   ordering生成canonical JSON。
5. 对canonical JSON的UTF-8 bytes计算SHA-256，输出64位lowercase hexadecimal。

Golden vector固定为
`bb16bfca66165acccafbdf63134f26ea480184d846b26491d29619a3ba2bae1b`；测试同时证明三组rows重新排序保持相同serialized
representation，而任一row value/state或membership变化都会改变hash。

Catalog row required：

- `catalogImportId`
- `sourceId`
- `title`
- `catalogKind`：仅`inscription | calligraphy`

Catalog row optional：

- `catalogId`
- tagged dynasty/date/region/current-location/custodian/description fields
- `ownerNote`

Alias row：`catalogImportId + alias + aliasType`，其中`aliasType`必填且仅允许
`alternate | historical`。`normalized_search`不是alias
type；搜索规范化是未来可重建的derived representation。

Provenance
row：`catalogImportId + sourceId + sourceTitle? + sourceTypeRaw? + sourceUrl? + sourceNote?`。`sourceTypeRaw`是raw
descriptive text，不是taxonomy、evidence quality、authority或publication
decision。Current apply要求每条Catalog row至少有一条相同
`catalogImportId + sourceId`的primary provenance
row；同一Catalog还可包含其他来源。

## 4. Field and persistence matrix

| Field/concept                    | Required    | Persistence disposition | Protection          | v1 apply behavior                                       |
| -------------------------------- | ----------- | ----------------------- | ------------------- | ------------------------------------------------------- |
| catalogImportId                  | yes         | RAW_ONLY / batch-local  | identity validation | retained in operation-item audit; never Catalog domain  |
| sourceId                         | yes         | SUPPORTED_NOW           | identity invariant  | primary provenance row required; durable linkage        |
| catalogId                        | update only | SUPPORTED_NOW           | identity invariant  | target only; never mutated                              |
| title                            | yes         | SUPPORTED_NOW           | Level B             | critical diff + field approval                          |
| catalogKind                      | yes         | SUPPORTED_NOW           | Level A             | structural diff + field approval                        |
| dynasty/dateText                 | no          | SUPPORTED_NOW           | Level B             | value/state persisted; changes require approval         |
| province/prefecture/county       | no          | SUPPORTED_NOW           | Level B             | value/state persisted; changes require approval         |
| currentLocation/currentCustodian | no          | SUPPORTED_NOW           | Level B             | value/state persisted; changes require approval         |
| description                      | no          | SUPPORTED_NOW           | Level C             | value/state persisted; CLEAR requires approval          |
| ownerNote                        | no          | RAW_ONLY                | Level C             | supplied input blocks before every write                |
| alias + aliasType                | child row   | SUPPORTED_NOW           | Level B             | create storage supported; ambiguous update fails closed |
| provenance metadata              | child row   | SUPPORTED_NOW           | Level B             | durable internal source record/linkage                  |

`summary`、`periodLabel`和curated Public citations虽已存在于read
model，但不属于v1 input；import必须保持其现值。Publication lifecycle、location
history、generated review、normalized source taxonomy与media属于FUTURE。Research
evidence、Owner research decisions/state、external ResearchRecord和SQLite
state是NOT_IMPORTED，不属于`catalog-import/v1` canonical input。

## 5. Blank, knowledge state and clear

Canonical tagged state是：

- `VALUE { value }`
- `UNSUPPLIED`
- `UNKNOWN`
- `NOT_APPLICABLE`
- `CLEAR`

XLSX/CSV使用paired value/state columns。规则：

| Value cell | State cell          | Canonical result |
| ---------- | ------------------- | ---------------- |
| nonblank   | blank or VALUE      | VALUE            |
| blank      | blank or UNSUPPLIED | UNSUPPLIED       |
| blank      | UNKNOWN             | UNKNOWN          |
| blank      | NOT_APPLICABLE      | NOT_APPLICABLE   |
| blank      | CLEAR               | CLEAR            |
| nonblank   | any non-VALUE state | validation error |
| blank      | VALUE               | validation error |

Required/identity fields没有state column。Factual nullable
fields允许全部state；description只允许VALUE、UNSUPPLIED与CLEAR。Owner
note和append-only provenance不提供destructive state。普通blank永远不是delete。

任何没有durable preservation的RAW_ONLY或DEFERRED_PERSISTENCE
finding都必须返回通用 `DEFERRED_FIELD_NOT_PRESERVED`；Approval不能授权silent
loss。当前唯一可由Owner提供且触发该规则的canonical
field是`ownerNote`。`ALIAS_TYPE_STORAGE_REQUIRED`与
`PROVENANCE_STORAGE_REQUIRED`从未被runtime emit，也没有durable historical
payload或consumer，已从current internal schema安全删除。

## 6. Identity conflict, critical change and approval

`IDENTITY_CONFLICT`与`CRITICAL_CHANGE`永久分开：

- Identity conflict：CatalogId mismatch/rebinding、update target不存在、SourceId
  rebound或existing SourceId→CatalogId
  association冲突。它不可approval，必须阻断batch。
- Critical
  change：CatalogKind、title、temporal、region、location、custodian、alias或provenance
  metadata等非identity事实变化。它可审核，但Level A/B必须field-level approval。
- Level C ordinary change可由batch approval覆盖；任何Level的CLEAR都要field-level
  approval。

Approval必须绑定：

- `importContractVersion`
- `canonicalInputSha256`
- `dryRunResultSha256`

`canonicalInputSha256`是validated canonical
envelope先按3.3的稳定业务键排序，再经UTF-8 RFC 8785-compatible canonical
JSON序列化后的SHA-256。XLSX styling、ZIP metadata、worksheet/CSV row order、CSV
BOM/quoting/newline不参与authorization hash。
`sourceArtifactSha256`只用于原文件audit。任何canonical semantic
input或dry-run变化都会使approval失效；只重排行不会使approval失效。

## 7. SourceId uniqueness and mirroring

- `01_Catalog.catalogImportId`与`01_Catalog.sourceId`各自在batch内全局唯一。
- supplied `catalogId`最多出现在一条Catalog row；额外来源进入`03_Provenance`。
- `03_Provenance`的`(catalogImportId, sourceId)`唯一；SourceId在同一batch只能解析到一个catalogImportId。
- Provenance可以在相同catalogImportId下镜像primary
  SourceId以补充metadata；这是同一SourceRecord的扩展，不是新source。镜像optional，重复pair是validation
  error。
- Additional provenance SourceId不得等于另一个Catalog row的primary SourceId。
- 跨batch遇到相同SourceId→CatalogId可以update/unchanged；不同linkage为non-approvable
  identity conflict。

## 8. Duplicate policy

Duplicate SourceId或identity mismatch是validation/identity
conflict，不是similarity candidate。Title
normalization、region、custodian、provenance与existing IDs只能产生
`DUPLICATE_CANDIDATE`和signals。Reviewer disposition仅有：

- `SAME_ENTITY_CANDIDATE`
- `DIFFERENT_ENTITY_CANDIDATE`
- `UNRESOLVED`

Candidate不能自动merge、重写CatalogId或解除apply
blocker。真正merge属于未来Owner/Admin workflow。

## 9. Workbook specification

Safe template：`catalog-import-v1-template.xlsx`，且只有四张sheet：

1. `01_Catalog`
2. `02_Aliases`
3. `03_Provenance`
4. `99_Instructions`

### 9.1 Authority and reproducible artifact

`catalog-import/v1` semantic contract与internal `catalog-import-xlsx/v1`
presentation/layout spec共同构成authority。Version-controlled dev-only
generator从这两个spec生成approved XLSX；generator不是production/runtime
dependency，apps、services、Public root与OpenAPI均不得依赖它。Observable OOXML
tests（而非某个XLSX library API）是长期compatibility boundary。

Root commands会自行build所需internal contracts，不要求未声明的手工前置步骤：

- `pnpm generate:catalog-import-template`
- `pnpm check:catalog-import-template`

`--check`在临时目录重建workbook并比较每个OOXML part的normalized observable
fingerprint，不覆盖committed artifact。ZIP container
metadata不属于reproducibility boundary；相同spec必须产生observable-equivalent
workbook。

### 9.2 Data sheet physical layout

Header顺序由executable contract constants冻结。三张data sheet的physical
layout为：

- Row 1：中文presentation header；
- Row 2：逐字exact machine header，也是standard Excel Table/filter header；
- Row 3：唯一空白editable row；
- Table refs分别为`A2:V3`、`A2:C3`、`A2:F3`。

Template不预铺固定data rows。Validation以compact OOXML rule覆盖Row 3至Excel
maximum row；不得因此创建maximum-row cells、row
objects、fills、borders或styles。Headers、Row 3、Table style
mechanism与未来实际生成的数据行才有presentation
styling。Identity输入cells使用text-preserving number format；state
columns只做轻微视觉分组；data sheets无merge、hidden
helper或formula，gridlines保持可见。

Frozen panes是observable workbook contract：

- `01_Catalog`：top 2 rows + first 4 columns；
- `02_Aliases`：top 2 rows + first 1 column；
- `03_Provenance`：top 2 rows + first 2 columns。

Categorical/state dropdown保留英文machine values，input
message使用中文解释。Required / optional / update-only / child-row required
presentation直接来自layout mapping，并由canonicalizers/Zod schema
tests自动绑定；它不是第二套business-rule source。任何presentation/schema
mismatch都必须阻断artifact freshness check。Row
1从该requiredness自动派生简洁中文后缀：required与child-row
required显示`【必填】`，update-only显示 `【更新时填】`，optional不显示后缀；Row
2 machine headers保持不变。

### 9.3 Instructions and machine metadata

`99_Instructions`按Owner usability排序：Owner快速开始 → Identity / State /
Location guidance → Field Guide → Advanced persistence / approval / hash notes →
Technical Metadata。Field Guide由同一个layout spec生成，列为`Sheet`、
`中文名称`、`Machine header`、`Requiredness`、`如何填写`、`示例`；requiredness与synthetic
examples均来自该layout authority，不在workbook中另行维护business rules。

Owner
guidance明确new/update、`UNKNOWN`/`UNSUPPLIED`/`CLEAR`、`blank ≠ delete`、`Import ≠ Publish`、duplicate不自动merge、三种identity的区别，以及行政区/具体地点/保管机构的区分。Template可包含明确标记为synthetic的说明示例，但三张data
sheet没有production、demo或synthetic Catalog rows。

Technical Metadata使用固定、visible、machine-locatable cells；future
parser不需要搜索自然语言：

| Cell  | Value                    |
| ----- | ------------------------ |
| `A68` | `Technical Metadata`     |
| `A69` | `workbookLayoutVersion`  |
| `B69` | `catalog-import-xlsx/v1` |
| `A70` | `importContractVersion`  |
| `B70` | `catalog-import/v1`      |

Workbook layout version不进入canonical envelope或semantic hash。Metadata
rows与cells不得hidden，也不得使用hidden helper sheet。

### 9.4 Compatibility and security boundary

Primary compatibility evidence是standard OOXML、public-library
reopen、observable OOXML tests与independent workbook import/render。Excel for
Mac实际打开/编辑仍需Owner environment smoke；Apple Numbers只提供non-blocking
best-effort evidence，不能削弱canonical contract。

Template不包含production data、hidden payload、macros、external
links/connections、formula、credentials、SQL、database
internals、`objectKey`、storage path/provider secrets、ORM或migration
metadata。Workbook是Owner/Editor working format，不是database、canonical runtime
source、permanent master或production batch；PostgreSQL仍是canonical runtime
source of truth。

## 10. CSV specification

CSV bundle文件：

- `00_manifest.csv`
- `catalog.csv`
- `aliases.csv`
- `provenance.csv`

Input接受UTF-8 optional BOM及单一LF或CRLF newline style；mixed
newlines、duplicate headers、unknown headers或case
variation均失败。Parser可以按header定位输入列，但canonical
serializer固定contract顺序，使用UTF-8 no BOM、LF、RFC 4180 quoting与final
newline。Empty/state semantics与XLSX完全相同，两个format必须进入同一canonical
schema与hash逻辑。

## 11. Alias and provenance persistence / update semantics

`catalog_aliases`当前可无损保存alias与required
`aliasType`；CREATE会同时写入两者。Storage capability不等于collection update
policy：v1尚未定义既有alias collection的replace、merge或delete
semantics，因此UPDATE只有在incoming alias set与persisted
set完全相同时可继续；任何差异都在dry-run/pre-write阶段fail closed。

Raw provenance写入internal `catalog_import_sources`，保存SourceId→CatalogId
linkage和
`sourceTitle`、`sourceTypeRaw`、`sourceUrl`、`sourceNote`。它不写入curated
`catalog_source_citations`，也不进入Public DTO。已存在provenance
metadata的变化是Level B critical finding，必须field-level approval。每条Catalog
row的primary SourceId必须在`03_Provenance`中有同一
`catalogImportId + sourceId`行；否则apply transaction fail closed并rollback。

## 12. Import Batch and audit contract

Import Batch记录batchId、version、input format、optional artifact
hash、canonical input hash、createdAt、per-table row
counts、dry-run、approval与optional appliedAt。Dry-run包含result
counts、findings、duplicate candidates、apply blockers和result hash。

Batch
phase是独立enum：`RECEIVED | VALIDATED | DRY_RUN_COMPLETE | AWAITING_APPROVAL | APPROVED | APPLY_BLOCKED | APPLIED | REJECTED`。它不替代dry-run
state或approval state；schema同时验证batch、dry-run与approval的row
counts、version/hash binding、finding approval及appliedAt invariant。

当前durable apply audit保存operation/version/input hash/dry-run hash/approval
hash、validation
context、每行CatalogImportId/SourceId/CatalogId/result与application result；
`result_json`不保存dry-run findings或blocker payload。历史A/A.1 blocker
enum因此从未成为durable audit compatibility surface。

Apply前置条件：dry-run PASSED、approval
APPROVED且三项binding一致、零error、零identity conflict、零unresolved
blocker。Batch phase、dry-run、approval、Catalog lifecycle与publication
state不得复用单一通用status。

## 13. Public, security and media boundary

- Internal import subpath不得进入Web/Admin/UI/Public API或OpenAPI。
- Owner notes、raw provenance、batch/approval/review、identity
  conflicts和internal persistence metadata永不进入Public DTO。
- v1不接收local file path、objectKey、CDN URL、storage provider
  detail或图片本体。
- Import成功不改变publication；v1不定义publicationIntent。
- Official Catalog与UGC继续隔离。
