# T05.4-B XLSX Parser, Convergence and Security

- Status: implemented on `codex/t05-4-b-xlsx-importer`; pending Owner review
- Baseline: `origin/integration/mvp@a729fe70c4eb3a81060fde9df7b91615f9b132ec`
- Import contract: `catalog-import/v1` (unchanged)
- Workbook layout: `catalog-import-xlsx/v1` (unchanged)

## Scope

T05.4-B adds an untrusted XLSX input adapter to `@moya/catalog-importer`,
hardens the frozen CSV physical format, creates deterministic internal
diagnostics and authorizes exactly this importer for controlled raw-source
access. It does not add a Public API, database migration, Admin UI, publication
workflow or production data import.

The approved repository workbook remains the input authority. T05.4-B does not
change its bytes, sheet names, headers, metadata cells, layout version or
canonical semantics.

## Trust boundary

The core XLSX parser accepts bytes. The path wrapper accepts only a caller-
supplied regular, non-symlink file; it never searches Owner directories,
downloads URLs, follows workbook authorization text or scans research storage.
The same bytes provide the source artifact audit hash, ZIP/OOXML checks and
ExcelJS parse. `sourceArtifactSha256` is never approval.

Before workbook modeling, the importer uses a lazy ZIP reader and strict XML
parser to enforce named limits on compressed bytes, expanded bytes, per-entry
size, compression ratio, entry count, XML part size, data rows and materialized
cells. It rejects invalid/encrypted ZIPs, unsafe or duplicate entry names,
missing package relationships, DTD/entities, malformed XML, VBA/macros,
ActiveX/OLE/embeddings, external relationships/connections/links, drawings,
comments and other hidden noncanonical payload parts.

Workbook preflight then requires exactly four visible sheets, visible fixed
metadata at `A68:B70`, exact versions, exact Row 2 machine headers, no data
outside frozen columns and plain-text canonical cells. Formulas (including
cached results), hyperlinks, numbers, dates, booleans, errors and rich text fail
closed. Identity strings such as `000123` therefore cannot be silently coerced
to `123`.

## Parser architecture

```text
strict CSV physical parser ─┐
                            ├─ shared tabular canonical assembly
bounded XLSX parser ────────┘  ├─ existing canonicalizers/Zod invariants
                               ├─ same canonical envelope/JSON/SHA-256
                               └─ same dry-run/approval/apply engine
```

Focused modules live under `services/catalog-importer/src/parsing`. Neither
format owns business validation after tabular extraction. There is no XLSX-
specific envelope, dry-run, approval or apply path. `applyCatalogImport`
continues to recanonicalize input, validate the supplied dry-run and approval,
recompute the dry-run in its transaction, check blockers, allocate IDs only when
safe, write audit/domain rows and commit atomically.

CSV keeps UTF-8 with optional BOM, RFC 4180 quoting and exact headers. T05.4-B
adds strict UTF-8 decoding, regular-file/bundle/resource checks and rejection of
mixed LF/CRLF without expanding accepted syntax.

## Diagnostics

`CatalogImportDiagnosticError` carries deterministically ordered internal
diagnostics with stable code, severity, category, source format and safe
location fields. When applicable, diagnostics include file or sheet, visible
1-based row, machine header and Excel cell reference. Messages do not include
database URLs, credentials, SQL internals, raw rows, private absolute paths or
raw stack traces.

Categories distinguish container/OOXML, unsafe content, version/metadata,
sheet/header layout, unsupported cells, tabular validation and canonical
cross-row invariants. Identity/dry-run/apply findings remain in the existing
frozen dry-run model.

## Format-agnostic authorization

Synthetic cross-format tests prove equivalent CSV and XLSX input yields equal
canonical envelopes, canonical JSON, row counts, canonical input hashes,
PostgreSQL dry-run results/hashes and final Catalog state. Formatting, row
order, ZIP metadata, filename and workbook layout version do not enter the
canonical authorization hash.

Workbook or CSV content cannot carry apply authorization. Approval remains
out-of-band and binds only `importContractVersion`, `canonicalInputSha256` and
`dryRunResultSha256`. Supplied `ownerNote`, identity conflicts, unresolved
duplicates and undefined alias collection mutations continue to fail closed.

## Controlled raw-source capability

Architecture authorization requires both:

```text
allowlist contains @moya/catalog-importer
+ package manifest rawSourceAccess = controlled-importer
```

The allowlist contains exactly that package. Frontend workspaces remain
permanently denied even if a manifest is forged, and no browser/public runtime
depends on the importer. The capability covers only explicitly supplied
`catalog-import/v1` CSV bundles or `catalog-import-xlsx/v1` workbooks; it does
not authorize SQLite, research repositories, legacy datasets, image archives or
directory crawling.

## Operational entry and limits

`catalog-import:validate-xlsx` performs explicit path preflight, parse,
canonicalization and PostgreSQL dry-run, then writes structured JSON with
`applied: false`. It has no apply import or approval parser. The P5 disposable
validation flow remains separate regression infrastructure.

Still unsupported: alias collection replace/merge/delete semantics, `ownerNote`
persistence, Importer Admin UI, production real-data import, publication
workflow and research evidence ingestion.
